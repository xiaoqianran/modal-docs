# 基于角色的访问控制 (RBAC)

<Callout variant="gated-feature">
RBAC 在<a href="/pricing">团队和企业计划</a>上可用。访问<a href="/settings/plans">工作空间设置</a>进行升级。
</Callout>

基于角色的访问控制 (RBAC) 使 Workspace 管理员能够更精细地控制谁可以访问和修改资源。

这对于保护生产特别有用，同时允许更广泛的开发和登台访问。

Modal的RBAC系统在两个层面上运行：

* **工作区角色** 控制整体工作区权限。
* **环境角色** 控制对各个环境的访问。

## 工作区角色

模态 [工作空间](/docs/guide/workspaces) 为一组用户组织模态应用程序和其他资源。这些角色控制整个工作区级别的访问。

所有工作区成员都具有决定其总体权限的三个角色之一：

* **所有者** — 对工作区中所有内容的完全读写访问权限，包括计费、工作区管理和所有环境。可以将任何角色分配给其他成员。
* **经理** — 与所有者相同，但不能修改所有者角色。
* **会员** — 可以部署和管理应用程序，但无法访问计费、工作区管理或其他工作区设置。

## 环境角色

模态[环境](/docs/guide/environments) 将模态应用程序和工作区中的其他资源相互隔离。

每个环境都有三个环境角色来决定对其的访问：

* **贡献者** — 对环境的完全读写访问权限。工作区所有者和管理员始终拥有贡献者访问权限。
* **查看者** — 对环境中资源的只读访问权限，包括仪表板、日志、指标、应用程序和功能配置。
* **无访问权限** — 没有对环境的读或写访问权限。

在常规环境中，工作区成员默认为 **贡献者**。在 **受限** 环境中，工作区所有者和管理员以外的成员使用环境的默认成员角色，该角色可以是 **贡献者**、**查看者** 或 **无访问权限**。工作区所有者和管理员始终拥有 **贡献者** 访问权限。
您可以将 **贡献者**、**查看者** 或 **无访问权限** 角色直接分配给受限环境中的工作区成员。直接分配的角色优先于默认角色。服务用户不使用成员默认值：他们在每个环境中默认为**无访问权限**，并且必须为他们需要的每个环境分配一个角色。

## 设置受限环境

从[环境设置](/settings/workspace-management/environments) 创建和管理受限环境。

您还可以使用 [`modal environment create --restricted NAME`](/docs/cli/latest/environment#modal-environment-create) 创建受限环境。

仅更改使用它的会员的默认更新访问权限。直接分配给成员的角色和服务用户角色保持不变。

### 演员的默认访问

|工作区角色 |不受限制的环境默认|受贡献者默认限制 |受查看器默认限制 |默认限制为无访问权限 |
| ---------------------------- | -------------------------------- | ----------------------------------- | ------------------------------------------ | --------------------------------- |
|工作区所有者 |贡献者 |贡献者 |贡献者 |贡献者 |
|工作区经理 |贡献者 |贡献者 |贡献者 |贡献者 |
|工作区会员 |贡献者 |贡献者 |观众|无法访问 ||服务用户/服务令牌 |无法访问 |无法访问 |无法访问 |无法访问 |

只能在受限环境中为工作区成员分配环境角色。可以从服务用户的[令牌设置](/settings/tokens/service-users) 或环境的角色中为服务用户授予**任何**环境上的角色（无论是否受限）。

### 无访问权限和工作区默认值

成员具有**无访问权限**的环境将从环境列表和选择器中省略。直接访问环境的尝试被拒绝。
默认为**无访问**的受限环境仍然可以是工作区的默认环境。 Modal 不会自动选择另一个可访问的环境。使用不可访问的默认值的操作会失败，因此成员必须明确选择他们可以访问的环境。

## 服务用户和服务令牌

[服务用户](/docs/guide/service-users) 是使用 API 令牌进行身份验证的编程身份。它们对于 CI/CD 管道、部署机器人和其他机器对机器通信需求非常有用。

与人类用户不同，服务用户没有工作区级别的角色；他们的访问完全通过环境角色控制。

|使用案例 |推荐身份|访问如何运作 |
| -------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
|交互式开发还是手动管理 |人类用户|访问权限基于用户的工作空间角色以及受限环境的任何环境角色 |
| CI/CD 或部署工作流程中的自动化 |使用服务令牌对服务用户进行身份验证 |访问权限仅基于服务用户的环境角色 ||部署到环境 |具有贡献者访问权限的人类用户或服务用户 |部署需要**贡献者**访问目标环境；向服务用户授予其部署到的每个环境中的角色 |

这使得服务用户成为推荐的方式，让自动化部署到特定环境，而无需授予广泛的工作空间权限。

## 代理代币

[端点](/docs/guide/endpoints)、[服务器](/docs/guide/servers) 和 [Web Functions](/docs/guide/webhooks) 上的 HTTP 接口可以使用 [代理令牌](/docs/guide/webhook-proxy-auth) 进行保护，这些令牌会在入站 HTTP 请求到达容器之前对其进行身份验证。
在启用 RBAC 的工作区中，代理令牌具有**范围** — 每个令牌都与一个或多个环境显式关联，并且仅被部署在这些环境中的端点接受。这可以防止用于暂存端点的令牌被用于调用生产端点。

### 创建作用域代理令牌

1. 导航到 **设置 → 代理令牌**，然后单击 **新令牌**。
2. 复制令牌 ID 和机密 — 机密仅显示一次。
3. 系统将提示您选择此令牌应有效的环境。
4. 使用任何现有范围令牌上的 **管理环境** 按钮来更新其环境关联。更改会立即生效，因此删除环境将立即撤销使用该令牌调用该环境中端点的任何客户端的访问权限。

或者，您可以通过 [CLI](/docs/cli/latest/workspace#modal-workspace-proxy-tokens) 或 [Python SDK](/docs/sdk/py/latest/Workspace#proxy_tokens) 创建和管理代理令牌。

### 作用域令牌与工作空间范围令牌

|代币类型 |谁得到它|有效期为 |
| -------------- | ---------------------------- | ---------------------------------------------------------------------- |
|范围 |启用 RBAC 的工作空间 |仅与令牌明确关联的环境 |
|工作空间范围 |没有 RBAC 的工作空间 |工作区中的任何 Web 功能 |

现有的工作区范围令牌继续按原样工作。默认情况下，在启用 RBAC 的工作区上创建的新令牌具有范围。

如果在工作区上禁用 RBAC，作用域令牌将回退到工作区范围的访问。

## 跨环境访问

受限环境阻止其他环境中的应用程序和任务身份访问受限环境内的资源。有关更多详细信息，请参阅[跨环境查找](/docs/guide/environments#cross-environment-lookups)。

实际上，这意味着任务可以访问其自己的环境和其他不受限制的环境中的对象，但在另一个环境中运行的代码无法使用`modal.App.lookup()`、`Secret.from_name()`或`Volume.lookup()`等API来访问受限制的环境。

这可以防止权限从不太受信任的环境升级到更敏感的环境。
### 应用程序和任务身份的跨环境行为

访问检查根据**目标**环境进行评估。这意味着在受限环境内运行的工作负载仍然可以访问**不受限制**环境中的对象，但在受限环境外运行的工作负载无法访问该环境。

|来源环境|目标环境|跨环境访问 |
| ------------------ | ------------------ | ------------------------ |
|无限制|无限制|允许 ||无限制|受限制 |被拒绝 |
|受限制 |无限制|允许 |
|受限制 |受限制 |被拒绝 |

同一环境访问不受这些跨环境规则的影响。

### 示例：入站访问与出站访问

假设您有两个环境：

* `prod` — 受限
* `test` — 无限制

在 `test` 中运行的任务无法在 `prod` 中查找机密、卷或应用程序。

在`prod`中运行的任务仍然可以访问`test`中的对象，因为`test`不受限制。
如果 `prod` 和 `test` 都受到限制，则一个中的任务无法访问另一个中的对象。

## 在受限环境中保护生产机密

常见的 RBAC 设置是将生产机密放置在受限的生产环境中，并仅向应允许部署或管理生产的人类用户和服务用户授予 **贡献者** 访问权限。

|场景 |结果 || ------------------------------------------------------------------------------------------ | -------- |
| `dev` 中的开发人员尝试编辑受限制的 `prod` 中的机密 |被拒绝 |
|具有对受限 `prod` 的贡献者访问权限的 CI 服务用户部署到 `prod` |允许 |
|在 `prod` 中运行的任务读取 `prod` 中的秘密 |允许 |
|在 `prod` 中运行的任务访问不受限制的 `test` 中的对象 |允许 |

此设置可让您保持开发和测试更加开放，同时保护生产资源（包括机密）免遭意外或未经授权的访问。

## 常见访问模式
|图案|允许吗？                     |笔记|
| ------------------------------------------------------------------------------------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------- ||工作区成员在受限环境中查看日志 |如果查看者或贡献者 |有效角色为无访问权限的成员无法发现环境 |
|工作区成员部署到受限环境 |如果贡献者 |部署或修改资源需要贡献者访问权限 |

|用户在受限环境中查看仪表板或应用程序详细信息 |如果查看者或贡献者 |查看者访问包括只读视图，例如仪表板、日志、指标和配置 |

## 常见问题解答

**我可以将环境设为完全私有吗？**

是的。将受限环境的默认成员角色设置为 **无访问权限**，然后仅将 **查看者** 或 **贡献者** 分配给需要它的工作区成员和服务用户。其他成员无法发现环境。工作区所有者和管理者始终保留**贡献者**访问权限。

**服务令牌如何在受限环境中工作？**

服务令牌对服务用户进行身份验证。服务用户在每个环境上默认为 **无访问权限**，无论是否受限，并且无法读取或写入环境，除非您为他们分配 **查看者** 或 **贡献者** 角色。这使得自动化系统和 CI/CD 管道可以部署和管理生产，而无需授予广泛的工作空间权限。
**我可以在不同的受限环境中使用`modal.App.lookup()`吗？**

不可以。应用程序无法在不同的受限环境中查找、读取或写入对象。

**在受限环境中运行的代码可以访问其他环境吗？**

是的，但仅当目标环境不受限制时。受限环境会阻止其他环境对其进行**访问**。
